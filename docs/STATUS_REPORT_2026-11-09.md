# 1. Bottom line

The code is where we left it in June. The last commit to main is 09a1278, dated June 12, 2026 (PR \#20, the species reference page), and nothing has been pushed in the five months since. I cloned the repository and ran what could be run from here: the backend tests (37 passed, 1 skipped), the frontend type check, and the production build. All three succeeded.

The app does what the March requirements asked of it. It tracks individual spawn and substrate bags from a sterilization or pasteurization run through inoculation, incubation, fruiting, two harvests and disposal. It keeps the lineage between bags and reports contamination and biological efficiency. As far as the record shows, no real bag has been entered in it. The last check, on June 10, found the production database holding only the seed defaults, and nothing in the repository suggests that has changed.

Three things stand between the app as built and an app the farm would use every week.

1.  **The operating gaps found in June are still open in the repository.** There is no sign-in. The Compose file has no restart policy and no scheduled backup, and it publishes the database port on the host. Bag codes still repeat their prefix (STER-STER-...). The vault holds no record that any of them was fixed on the server after June 10.

2.  **The dependencies have aged.** npm audit reports six advisories against the locked frontend packages, one of them rated critical against the installed Next.js 16.2.4. On the backend, starlette 0.48.0 carries six advisories.

3.  **The farm has changed more than the code has.** You now inoculate substrate from purchased grain spawn, which the app has no way to record. Production is about 50 pounds a week across six varieties, sold at farmers markets, with a restaurant channel being built this winter. The app knows one species and stops at the harvest weight of a single bag.

Two events since the first version of this report come ahead of all of that. Your laptop's drive failed and took with it the only SSH key to the droplet, a key the vault says was also used on your other droplets. Claude Code's check then found two Anthropic API keys stored in plain text in the vault repository. Part 9 now begins with regaining access and rotating those keys.

I recommend settling the specification before any more code is written. Part 8 lists the changes I would make. The SRS delivered with this report already includes them, each marked as proposed so that you can strike or change it.

# 10. My assessment

In June I said the app was worth continuing if it got used. It has not been used, and I think part of the reason is the app itself. As built it asks for six separate entries on every substrate bag (incubation, ready, fruiting, two harvests, disposal), each made one bag at a time by typing or scanning a code. If the farm starts 40 substrate bags a week, that is about 240 entries a week before anything is learned from them. The information is worth having. It tells you which runs contaminate and which varieties and recipes pay. The current screens charge too much labor for it.

The changes in Part 8 that matter most are therefore the ones that reduce entries: automatic incubation start, whole-run steps, group harvest weights and camera scanning. With those in place a run of bags that behaves normally would need a handful of entries in total, and single-bag entries would be reserved for exceptions such as a contaminated bag.

There is a simpler alternative and you should weigh it. A spreadsheet with one row per pasteurization run would give you yield by run and variety with a fraction of the effort. It would not give you lineage or contamination tracing. If contamination has not been a recurring problem at the farm, the spreadsheet is a defensible choice and the app could wait until the farm is larger. If you intend to make your own liquid culture and grain spawn again, lineage starts to matter, because one bad culture can spoil every bag downstream of it and the app is built to show exactly that.

The engineering is in good shape. The tests, the contract checks and the automatic deployment mean changes can be made quickly and safely through Claude Code. The remaining work in steps B through D is small next to what has already been built. The risk lies in building further ahead of use, which is what happened between March and June.

The loss of the laptop adds one consideration. No real data was ever entered, and in June the app could not be reached at all, so the droplet almost certainly holds nothing worth recovering. If getting back into it proves slow, building a fresh droplet from GitHub is a sound course and the hardening in step B could be built in from the start. I have not looked at your other droplets and this reasoning may not hold for them.

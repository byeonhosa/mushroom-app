# Decisions

Design and scope decisions made by the lead developer, newest last. The owner's own decisions on the SRS's open questions are in `docs/LEAD_DEVELOPER_BRIEF.md` section 4 and are not repeated here. Each entry says what was decided, why, and how to reverse it.

| # | Date | Decision | Why | To reverse |
|---|---|---|---|---|
| D-001 | 2026-11-11 | CI runs on `ubuntu-latest` again, with Playwright kept current by Dependabot. | The `ubuntu-24.04` pin was a stopgap for Playwright 1.58. A pinned image fails outright the day GitHub retires it; a floating image with a current Playwright fails only if Playwright falls behind. | Set `runs-on` back to a fixed image in `.github/workflows/ci.yml`. |
| D-002 | 2026-11-11 | The backend installs from hashed lockfiles (`requirements.txt`, `requirements-dev.txt`) compiled from `requirements.in` files. `pip-audit` runs in CI from its own pinned install and is not in the lockfile. | MNT-7. Hashes make every build install byte-identical packages. `pip-audit` pulls in forty-odd packages that the app never imports. | Delete the `.in` files and maintain `requirements.txt` by hand. |
| D-003 | 2026-11-11 | Dependency audits gate every pull request: any `pip-audit` finding, and any `npm audit` finding rated high or critical in a production dependency. An accepted exception is added to the CI command with `--ignore-vuln` and recorded here. | SEC-4. A gate that only warns is not read. | Remove the `dependency-audit` job. |
| D-004 | 2026-11-11 | Backups are a Compose service built from `postgres:16`, not a host cron job, and the old Python backup scripts are removed. Daily dumps keep 14 copies; a separate pre-deploy dump is taken before every deploy and keeps 5. | The droplet can only be changed through the deploy workflow. `pg_dump` in the API image would not match the server version for long. Pre-deploy dumps are kept apart so that a day of many deploys does not push out the daily copies. | Remove the `backup` service; nothing else depends on it. |
| D-005 | 2026-11-11 | A restore test runs on every deploy and in CI, into a scratch database. | REL-3 asks for a test every three months. Run on every deploy it costs seconds and cannot be forgotten. | Delete the workflow step. |
| D-006 | 2026-11-11 | The API and frontend ports are bound to `127.0.0.1` now, ahead of the proxy in WP-2. | Nothing could reach them through the firewall anyway, and the firewall should not be the only protection. The deploy smoke tests use the loopback address. | Change the `ports` entries in `docker-compose.yml`. |
| D-007 | 2026-11-11 | The `zones` table is dropped (migration 023). | The roadmap asked for a decision. Its seed rows (a mixing area, an incubation tent, fruiting tents) do not describe the farm's sites, and nothing has referred to it since March. Bag location (BAG-10) needs site and room, and will get a table designed for that. | Recreate the table in a new migration. No data is lost: it held three seed rows. |
| D-008 | 2026-11-11 | A time sent to the API without a UTC offset is refused (422). Every time in a response is UTC with its offset. | SRS 5.2. A time with no offset would be stored as if it were UTC, four or five hours off for an Eastern farm, and the mistake would be invisible. The screens already send an offset. | Change `InputDatetime` in `backend/app/schemas.py` to accept naive values and decide which zone they mean. |
| D-009 | 2026-11-11 | A run's planned bag count is limited to 999. | RUN-3 needs an upper bound to keep bag numbers within the label format (BAG-5). The farm starts fewer than 100 substrate bags a week. | Raise `le=999` in the run schemas; bag codes for such a run would exceed 18 characters. |
| D-010 | 2026-11-11 | Status `CREATED` is no longer produced. A bag with no stage recorded reads `STERILIZED` or `PASTEURIZED`. | MNT-3. The two old code paths differed exactly here. SRS 3.2 says a bag record is created from a run that has already been heat-treated, and no screen or filter knew `CREATED`. | Restore the branch in `_derive_bag_status`. |
| D-011 | 2026-11-11 | A run code must be six digits and a capital letter (`261109A`). The API refuses anything else; the form proposes the code from the unload date and the operator can change the letter or the date. | The owner fixed the bag code format (brief, decision 4), and the run code is part of every bag code. A free-text run code cannot be guaranteed to fit 18 characters. A proposal that is almost always accepted costs the operator nothing. | Loosen `_clean_run_code` in `backend/app/schemas.py`. Bag codes for a free-text run code fall back to the cleaned run code and may exceed 18 characters. |
| D-012 | 2026-11-11 | A species code is two or three capital letters or digits. | It is printed in every bag code. Three characters is the most that keeps the longest code (a 999-bag run) at 18. Eighteen varieties fit easily: LM, BO, BKO. | Widen the pattern in `_clean_species_code`; accept bag codes of 19 characters or more. |
| D-013 | 2026-11-11 | The bag number in a code is the bag's place in its run, counted across species and sessions, two digits (three for a run planned for 100 bags or more). | The SRS says "the bag's number in the run". A number that restarted for each species would repeat within a run and could not be read off a shelf count. | Change `_generate_bag_codes` in `backend/app/bag_id.py`. Codes already issued stay as they are. |
| D-014 | 2026-11-11 | Internal bag IDs are issued from a counter table (`id_counters`, migration 024) updated inside the creating transaction, and an inoculation session locks its run row before choosing bags. | BAG-11. A PostgreSQL sequence would not exist on the SQLite test database; a counter row works on both and its row lock queues concurrent requests. The run lock was added after the concurrency test showed two sessions choosing the same unlabeled bags. | None needed. The table is two rows. |
| D-015 | 2026-11-11 | Sessions are rows in the database. The cookie (`mfa_session`: HttpOnly, SameSite=Lax, Secure whenever the request arrived over HTTPS) carries a random 256-bit token; only its SHA-256 digest is stored. A session ends after 14 days unused or 30 days in all. | USR-3 and the April design. A server-side session can be ended at once (sign-out, deactivation, password reset); a signed token cannot. The lifetimes suit a phone used most days at the farm. | Change `session_idle_days` and `session_max_days` in `backend/app/config.py`, or set them in the environment. |
| D-016 | 2026-11-11 | Passwords are hashed with bcrypt at work factor 12, and must be 10 to 72 characters. | The April design named bcrypt. It reads at most 72 bytes, so a longer password is refused instead of being silently cut short. | Replace `backend/app/security.py`; existing hashes would need a migration path at next sign-in. |
| D-017 | 2026-11-11 | A state-changing request must carry an Origin or Referer naming the app (its own host, `https://APP_HOSTNAME`, or an origin in `CORS_ORIGINS`). One with neither is refused. | Roadmap WP-2. It is the second lock beside the SameSite cookie. A browser always sends Origin on a POST, so only scripts are affected, and they can send the header. | Remove the `enforce_same_origin` dependency in `backend/app/main.py`. |
| D-018 | 2026-11-11 | An operator may create mix lots, liquid cultures and ingredient lots as well as runs, bags and events. Species, grain types, fill profiles, ingredient definitions and users need an administrator. | The SRS lists all of these under reference data, but a mix lot is made for every pasteurization run. If only an administrator could record one, an operator could not record a day's work. | Add `dependencies=ADMIN_ONLY` to those routes in `backend/app/api.py`. |
| D-019 | 2026-11-11 | The first administrator is created by a one-off container in the deploy workflow (`python -m app.manage bootstrap-admin`) from two GitHub secrets, and the deploy's signed-in check uses a two-minute session made on the server (`smoke-session`). | The password never sits in the long-running container's environment, and the check keeps working after the owner changes that password, which the app asks for at first sign-in. | Set the two variables in the droplet's `.env`; the API also reads them at startup. |
| D-020 | 2026-11-11 | The pages call the API on their own origin, at `/api`. `NEXT_PUBLIC_API_BASE` is gone. Without a proxy in front, the frontend forwards `/api/*` itself (`API_PROXY_TARGET`). | Status report finding F5: the address baked into the June build made the app unusable from anywhere. One origin also means the session cookie needs no CORS. | None needed. |
| D-021 | 2026-11-11 | In production a sign-in over plain HTTP is refused unless it comes from the server itself or a private address. | SEC-1. Until a hostname and certificate exist the proxy can only offer HTTP; a password must not cross the internet that way even if the firewall is opened early. | Remove `refuse_plaintext_sign_in` from the login route. |
| D-022 | 2026-11-11 | The menu collapses behind a button on screens narrower than 980 pixels, ahead of WP-5. | Looking at the sign-in work on a phone showed the 17-link menu fixed over a third of the screen. Sign-in from a phone is part of WP-2's outcome. | Delete the `.menuToggle` rules in `frontend/app/styles.css`. |
| D-023 | 2026-11-11 | Production does not serve the interactive API documentation (`/docs`, `/redoc`, `/openapi.json`). | It describes every route to anyone who asks. The contract is in the repository (`frontend/lib/generated/openapi.json`). | Remove `_docs` in `backend/app/main.py`. |
| D-024 | 2026-11-11 | The proxy is Caddy, built into its own image with the Caddyfile inside, publishing ports 80 and 443. It serves HTTPS automatically when the repository variable `APP_HOSTNAME` is set and plain HTTP on port 80 when it is not. | Brief, decision 7. A built image means a changed Caddyfile reaches the server on the next deploy, with no reload step to forget. CI runs the HTTPS path with a certificate Caddy signs itself (`tls internal`), so the production path is tested without a public name. | Remove the `proxy` service; the API and frontend stay reachable on the loopback ports. |
| D-025 | 2026-11-11 | Dependabot does not propose new major versions of PostgreSQL, Node or Caddy, nor new minor versions of Python. | Its first run proposed PostgreSQL 16 to 18, which cannot read the existing data volume and would have stopped the database, and Python 3.15 and Node 26 without CI or the lockfiles moving with them. These are upgraded deliberately, in one pull request each. | Delete the `ignore` entries in `.github/dependabot.yml`. |
| D-026 | 2026-11-11 | Content-Security-Policy allows inline scripts and styles from the app's own origin and nothing from any other origin. | Next.js starts each page with inline scripts; a nonce-based policy would need every page rendered per request. Nothing is loaded from third parties, so `'self'` covers the rest. | Edit `ops/proxy/Caddyfile`. |
| D-027 | 2026-11-11 | Species codes, slugs and names are the farm website's own (BO `blue-oyster`, LM `lion-s-mane`, KT `king-trumpet` and so on), loaded from `backend/app/seeds/species.json`. A test fails if the two lists drift. | Brief section 10 asks for a stable public identifier. Using the website's existing ones means the integration needs no mapping table for species. The website says `lion-s-mane`, not the brief's example `lions-mane`, and calls king oyster King Trumpet. | Change the seed file and the test; a slug already in the database cannot be changed through the app. |
| D-028 | 2026-11-11 | The four website fields are stored on the species: `availability_tier` (the website's tier values), `sale_path` (the website's nine availability states; a new species is `hidden`), `in_rotation_now` (true or false, the farm's own fact), and `restrictions` (free text; `legal-review` where the website requires legal review before any health claim). | The brief names these four fields and asks that their values stay within the website's vocabulary. The website has no fields called `sale_path` or `restrictions`; its availability state and `requiresLegalReview` are the nearest things. The integration API (WP-9) can rename on the way out. | A migration renaming the columns. |
| D-029 | 2026-11-11 | A cultivation profile stays in its own table, one row per species, linked by `species_id`, and is not merged into the species table. | Thirty-five profile columns would crowd the table every bag query joins. One row per species, enforced by a unique key, gives the same guarantee as merged columns. | A migration that copies the columns across. |
| D-030 | 2026-11-11 | The species seeder only adds. It never changes a name, an active flag, a slug that is set, website fields that are set, or an existing profile. `--refresh-profiles` replaces profiles on purpose. | It runs at every container start. Without this rule an administrator's change would be undone by the next deploy. | Edit `backend/app/seed_species.py`. |
| D-031 | 2026-11-11 | The four oyster varieties share the farm's one oyster profile, marked as from the farm's sources and as generic. Black king oyster uses the King Trumpet profile, marked researched. | The farm's sources describe one oyster. Splitting it four ways with invented differences would be worse than saying plainly that it is shared. | Edit `backend/app/seeds/species.json` and run the seeder with `--refresh-profiles`. |
| D-032 | 2026-11-11 | Anyone signed in can read the species list; only an administrator can change it. | An operator needs to see codes and names. The menu entry was administrator-only before. | Set `adminOnly` on the menu entry in `frontend/app/app-shell.tsx`. |
| D-033 | 2026-11-11 | A purchased spawn lot is its own record, not a bag. It has no status events and no label; it is "open" until someone marks it used up, and can be reopened. Inoculating from it consumes nothing. | REF-11, INO-6, INO-7 and brief decision 3. A lot is a box of several supplier bags used across days; modelling it as one spawn bag would force the consumed-on-first-use rule on it and would put supplier material into bag counts and biological-efficiency figures. | Migration that drops `purchased_spawn_lots` and the two `source_purchased_spawn_lot_id` columns; bags inoculated from a lot would lose their source. |
| D-034 | 2026-11-11 | A lot's code is `PL-{species code}-{date received as YYMMDD}{letter}`, issued by the app (for example `PL-BO-261111A`). | It reads like a bag code, sorts by species and date, and needs no typing. The supplier's own lot number is kept beside it for a recall or a complaint. | Change `_next_purchased_lot_code` in `backend/app/crud_reference.py`; codes already issued stay. |
| D-035 | 2026-11-11 | Spawn bags inoculated from a purchased lot are generation 1 (the same as spawn from a liquid culture). Substrate inoculated straight from a purchased lot is generation 0 and reads "Straight from purchased spawn" in reports. | TRC-3. Generation counts the farm's own grain transfers. Bought spawn has an unknown history, and the useful comparison is bought spawn used directly against the farm's own expansions of it. | Change `_spawn_generation_for_bag` and its label in `backend/app/crud_reporting.py`. |
| D-036 | 2026-11-11 | Any signed-in user can record a purchased lot, mark it used up, reopen it or deactivate it. A lot's species cannot be changed once bags have been inoculated from it. | Same reasoning as D-018: receiving a delivery is a day's work, not administration. The species lock keeps bag codes, which carry the species, true to their source. | Add `dependencies=ADMIN_ONLY` to the three routes in `backend/app/api.py`. |
| D-037 | 2026-11-11 | The setting that would let one of the farm's own spawn bags serve several sessions is deferred to WP-4. | Brief decision 3 asks for it as an administrator setting. No settings table exists yet; WP-4 adds one for the flush limit and the weight unit, and this setting belongs with them. Today's rule (consumed by the first session) is the brief's default, so nothing the farm does is blocked. | None needed. |
| D-038 | 2026-11-11 | The substrate inoculation screen opens on "Purchased spawn lot" when an open lot exists, and on "Spawn bag" when none does. | The farm buys most of its spawn today (status report, change C1), so the common case should need the fewest taps. | Change the default in `frontend/app/events/inoculation/page.tsx` and the pasteurization run page. |
| D-039 | 2026-11-11 | The demo data generator is a simulation. It keeps a diary of steps in time order and performs each one through the same functions the screens call, with the app's clock (`app.clock`) set to the moment the step would have happened. It writes no row directly. | Brief section 7. A table loader would have to copy the rules for bag codes, statuses, events and lineage, and would drift from them. Run this way the generator is also the widest test of those rules: it found nothing wrong today, and it will fail loudly when a rule changes without it. The cost is speed: about 35 seconds per thousand bags on PostgreSQL. | Write rows directly in `backend/app/seed_demo.py`; `app.clock` can stay. |
| D-040 | 2026-11-11 | The generator refuses a database that holds any sterilization run, pasteurization run, bag, purchased lot, liquid culture or harvest, and separately refuses when `APP_ENV` is production. Each has its own flag. Reference rows and mix lots do not count. | Brief section 7. Two flags because they are two different mistakes: adding demo bags to real ones, and running on the farm's server at all. Mix lots are left out because migration 015 seeds one, so every new database would be refused. | Edit `_FARM_TABLES` and `_check_allowed` in `backend/app/seed_demo.py`. |
| D-041 | 2026-11-11 | The generated story ends at 6 pm on the end date, which is yesterday unless given. The result depends only on seed, scale, weeks and end date. | "Deterministic" has to mean something checkable: a test generates twice and compares a digest of every bag, event and weight. Ending yesterday means nothing is ever stamped in the future. | Change `_Simulation.__init__`. |
| D-042 | 2026-11-11 | Scale multiplies the number of runs a week (two pasteurization runs and half a sterilization run at scale 1), not the size of a run. Harvests stop at two flushes. | A run of 400 bags is not what a busy farm looks like; more runs is. Scale 10 gives the 10,000-bag dataset the brief asks for. The app accepts only flush 1 and 2 until HAR-3 (WP-4); the generator has one constant to raise then. | Change the constants at the top of `backend/app/seed_demo.py`. |
| D-043 | 2026-11-11 | Reference records are never deleted, used or not. Spawn recipes, substrate recipes, fill profiles, grain types, ingredients, liquid cultures and purchased lots each have an active flag; a deactivated one stays on every list and on the records that used it, is left out of the pick lists, and is refused by the API for a new run or mix lot. | REF-14 asks this for records in use. Applying it to all of them means one rule, no "is it in use?" query to get wrong, and nothing an administrator can destroy by a slip. | Add delete routes that check for use first. |
| D-044 | 2026-11-11 | Only an administrator adds or changes recipes, fill profiles, grain types and ingredients. Any signed-in user can read them, and can add, annotate and deactivate liquid cultures. | Follows D-018: an operator records a culture or a mix lot as part of a day's work; a recipe or a fill profile changes what every later bag means. | Change `dependencies=ADMIN_ONLY` on the routes in `backend/app/api.py`. |
| D-045 | 2026-11-11 | Editing a fill profile's weights changes bags created afterwards only. A substrate recipe has no version number: a changed recipe is entered as a new recipe and the old one deactivated. | A bag copies its target dry weight when it is created, so past biological-efficiency figures do not move when a profile is corrected. The table is called `substrate_recipe_versions` and each row already is one version; a second versioning scheme on top would be two ways to say the same thing. | Add a `version` column and group recipes by name. |
| D-046 | 2026-11-11 | A liquid culture's code and species cannot be changed once it exists. Its parent, when given, must be of the same species and must not be the culture itself or a descendant. | Bag codes carry the species, and lineage reports key on the culture. A loop in the parent chain would hang any walk up it. | Loosen `LiquidCultureUpdate` in `backend/app/schemas.py` and `_check_culture_parent` in `backend/app/crud_reference.py`. |
| D-047 | 2026-11-11 | A run can be corrected after it is created, within limits set by what already rests on it. Its recipe, grain and mix lot are fixed once it has bag records; its code once any of its bags has a label; its planned count cannot go below the records that exist, and cannot cross 100 once labels exist. | RUN-5 says only "edit a run's details". Bags copy the run's recipe when their records are created and print its code when labelled, so a later change would make the run and its bags disagree, or leave printed labels naming a run that no longer exists. Crossing 100 changes the width the bag number is printed with (D-013). | Remove the checks in `_correct_run` in `backend/app/crud_reference.py`. |
| D-048 | 2026-11-11 | Correcting a record of work (a run, a mix lot) is for an administrator; recording it is for anyone signed in. A mix lot's recipe and fill profile are fixed once a pasteurization run uses it. | RUN-5 gives run corrections to an administrator, and a mix lot is the same kind of record. An operator who makes a slip asks for it to be put right, which is one more pair of eyes on a change to history. The lot's composition is what its runs and their bags were made with. | Remove `dependencies=ADMIN_ONLY` from the PATCH routes in `backend/app/api.py`. |
| D-049 | 2026-11-11 | The ingredient-lot form no longer asks for a unit cost. The column and the API field stay. | The owner decided against cost tracking (brief, section 4), and SRS REF-7 notes the field was used by nothing. A field that invites data nobody reads is a small tax on every delivery. | Add the input back in `frontend/app/ingredients/page.tsx`. |
